# CLAUDE.md

## Structure

Multi-plugin layout: one marketplace at root `.claude-plugin/marketplace.json`, each plugin self-contained under `plugins/<name>/.claude-plugin/plugin.json`. No `.github/plugin/`: that duplicate-manifest approach was dropped, since `.claude-plugin/` alone is discovered by both Claude Code (natively) and Copilot CLI/VS Code Agent Plugins (as a documented fallback location).

Each plugin's skills/hooks/instructions must live *inside* that plugin's own directory tree. Installation only copies a plugin's declared root subtree.

## Validating config changes

To test either plugin end-to-end from a local checkout before pushing:

```
/plugin marketplace add <local-path>              # Claude Code
copilot plugin marketplace add <local-path>        # Copilot CLI
```

To verify what Copilot CLI *actually* resolves at runtime (not just what docs claim): `copilot plugin marketplace add .`, `copilot plugin install <plugin>@<marketplace-name>`, then re-run with `--log-level debug --log-dir <dir>` and grep the log for `hook stdout` / `Executing hook`. Inspect `~/.copilot/installed-plugins/<marketplace>/<plugin>/` to see exactly what got copied. Clean up with `copilot plugin marketplace remove <name> --force`.

Schema gotcha: Copilot's plugin.json requires `mcpServers`/`lspServers` as an object (Claude's schema also allows array); omit these fields entirely when unused rather than `[]`/`{}`.

Copilot CLI sets Claude-compatible env vars (`CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA`) alongside its own when spawning plugin hooks, undocumented but confirmed by direct testing: this is why a single Claude-format `hooks.json` works for both tools without a Copilot-specific twin.

Superseded 2026-08-25 (Copilot CLI 1.0.78, live-tested end-to-end, including installing `soul` via `copilot plugin marketplace add . && copilot plugin install soul@agent-instructions` and driving real `copilot -p` sessions with `--log-level all`): the 2026-08-05 note above ("only `SessionStart` fires") undercounted what a plugin's `hooks.json` gets, and overcounted what fixes it.

- `SessionStart` **and** `UserPromptSubmit` entries in a plugin's own `hooks/hooks.json` DO fire on Copilot CLI, with a Claude-compatible payload (`hook_event_name`, `tool_name`, etc.). Directly observed via `[hook stdout]` lines in the debug log for `general-instructions.ps1` and both `remind-*.ps1` scripts.
- `PreToolUse` (and presumably `PostToolUse`) entries in a plugin's own `hooks/hooks.json` do **not** fire, full stop, regardless of matcher content, tool name, or file naming inside the plugin's `hooks/` subtree. This is not a matcher/tool-name problem (same conclusion as 2026-08-05, still holds for the plugin-install path specifically).
- `PreToolUse` DOES fire, with the same Claude-compatible schema, from a hook config placed directly at the **global** `~/.copilot/hooks/*.json` (any filename; both the flat rtk-style array and Claude's nested `{"matcher":..., "hooks":[...]}` group form work there). Project-scoped `.github/hooks/*.json` was also tested and does **not** fire.
- Copilot CLI remaps its own tools to Claude-style names for the hook payload, but with Copilot's own field names, not Claude's: shell (`bash`/`powershell`) → `tool_name:"Bash"`, `tool_input.command` (matches Claude); its `create` tool → `tool_name:"Write"`, `tool_input.path` + `tool_input.file_text` (Claude uses `file_path`/`content`); its `edit` tool → `tool_name:"Edit"`, `tool_input.path` + `tool_input.old_str`/`new_str` (Claude uses `file_path`/`old_string`/`new_string`). A hook script reading only Claude's field names finds nothing even once discovery is fixed; `guard-em-dash.ps1` now probes every known spelling.

**Fixed 2026-08-25** (same session, later): the plugin-hooks `PreToolUse` gap above was a manifest issue, not a hard platform limitation. Adding an explicit `"hooks": "./hooks/hooks.json"` field to `plugins/soul/.claude-plugin/plugin.json` (validated by the schema's `^\./.*` pattern requirement, surfaced as an IDE diagnostic the moment the field was added without the `./` prefix) makes Copilot CLI dispatch `PreToolUse` from the installed plugin too, live-confirmed: `copilot -p` denied a file write containing an em dash with the exact `guard-em-dash.ps1` reason text, and allowed a clean write through. Without that explicit `hooks` field, Copilot CLI's plugin loader apparently only wires up a subset of events (`SessionStart`, `UserPromptSubmit`) by convention and needs the field to pick up the rest (`PreToolUse`, presumably `PostToolUse` too, untested). Claude Code itself doesn't require the field (convention-based `hooks/hooks.json` discovery already covers everything for it), and adding it alongside didn't break Claude Code. Net effect: `soul`'s em-dash guard now works via plugin install alone on Claude Code, Copilot CLI, and (per user report, matcher fix from earlier in this session) VS Code Copilot Chat, no per-machine or per-repo workaround file needed anywhere.

Separately, VS Code Copilot Chat (a different binary from Copilot CLI, with its own hook loader) DOES dispatch `PreToolUse` from a plugin's `hooks/hooks.json` (confirmed by user report: fixing the matcher, not the discovery path, fixed it there). Its own file tools are named `createFile`/`editFiles` (per `microsoft/vscode-copilot-chat`'s `docs/tools.md`), not Claude's `Write`/`Edit`, so a matcher hard-coded to Claude Code's tool names silently never triggers on VS Code either, even though the hook process itself is correctly discovered. The fix applied here: `plugins/soul/hooks/hooks.json`'s `PreToolUse` entry no longer sets a tool-name `matcher` at all, and `guard-em-dash.ps1` no longer branches on `tool_name`, instead probing `tool_input` for every known field-name spelling of "file path" and "new content" across Claude Code, Copilot CLI, and VS Code Copilot Chat, treating "none present" as "not a file-write call." An unrecognized future tool shape fails safe (silently skipped) rather than failing to enforce the rule. Microsoft's own hook reference (`microsoft/vscode-copilot-chat/assets/prompts/skills/agent-customization/references/hooks.md`) additionally documents workspace-level `.github/hooks/*.json` and user-level `~/.claude/settings.json` as hook sources VS Code reads independently of any plugin, useful if per-repo or per-machine hooks are ever needed there.

For hooks that fire under both tools but need to branch on vendor, prefer an opt-in check for Claude Code (`$env:CLAUDECODE`) over an opt-out check for Copilot (`$env:COPILOT_CLI`): opt-out requires enumerating every non-Claude host in advance to stay safe, opt-in fails closed by default against anything unverified, including hosts that don't exist yet. Don't use `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA` to detect Claude Code specifically: Copilot CLI deliberately mirrors those onto its own value for compatibility, since its `hooks.json` commands reference `${CLAUDE_PLUGIN_ROOT}` too. `CLAUDECODE` has no such reason to be spoofed (no functional need, no `COPILOT_CODE` counterpart observed) and is the more reliable positive signal for "this is genuinely Claude Code," though this couldn't be verified against a fully standalone Copilot CLI process, only inferred: every Copilot CLI invocation tested here was itself spawned as a subprocess of a live Claude Code session (via the Bash tool), which inherits `CLAUDECODE` from that parent regardless of what Copilot sets, so its presence in that one test dump is explainable by ordinary process inheritance rather than Copilot setting it itself. Re-verify with a truly standalone Copilot CLI session (no Claude Code parent process) before fully trusting this in a security-sensitive context.
